### `Agent`
**Table:** `agents`  
**ID type:** `String` (e.g. `"A1"`)

| Field | Type | Notes |
|---|---|---|
| `id` | `String` | Primary key, manually assigned |
| `name` | `String` | Agent display name |
| `activeOrderCount` | `int` | Defaults to `0`; used for load-balancing |
| `status` | `AgentStatus` | Current availability state |
| `orders` | `List<Order>` | Lazy-loaded; mapped by `assignedAgent` |

**Status enum — `AgentStatus`**

| Value | Meaning |
|---|---|
| `AVAILABLE` | Agent can receive new orders |
| `BUSY` | Agent is at capacity |
| `OFFLINE` | Agent is unreachable — triggers the T-4 agentic re-planning loop |

---

### `Order`
**Table:** `orders`  
**ID type:** `String` (e.g. `"O1"`)

| Field | Type | Notes |
|---|---|---|
| `id` | `String` | Primary key, manually assigned |
| `description` | `String` | Free-text order details (stored as TEXT) |
| `status` | `OrderStatus` | Current lifecycle state |
| `createdAt` | `LocalDateTime` | Auto-set via `@PrePersist` |
| `assignedAgent` | `Agent` | FK → `agents.id`; nullable (unassigned orders) |

**Status enum — `OrderStatus`**

| Value | Meaning |
|---|---|
| `ASSIGNED` | Order has an agent |
| `REASSIGNMENT_PENDING` | A `ReassignmentSuggestion` exists and awaits ops approval |
| `REASSIGNED` | Ops accepted a suggestion; order belongs to the new agent |
| `DELIVERED` | Order is complete |

### `ReassignmentSuggestion`
**Table:** `reassignment_suggestions`  
**ID type:** `Long` (auto-generated)

| Field | Type | Notes |
|---|---|---|
| `id` | `Long` | Auto-generated primary key |
| `order` | `Order` | FK → `orders.id`; the order needing reassignment |
| `recommendedAgent` | `Agent` | FK → `agents.id`; nullable if AI returned invalid ID |
| `confidence` | `Double` | LLM confidence score, clamped to `[0.0, 1.0]` |
| `reasoning` | `String` | Plain-English LLM rationale shown in the ops UI |
| `status` | `SuggestionStatus` | Lifecycle state (default: `PENDING`) |
| `triggerReason` | `TriggerReason` | What caused this suggestion to be created |
| `createdAt` | `LocalDateTime` | Auto-set via `@PrePersist`; immutable after insert |
| `resolvedAt` | `LocalDateTime` | Set when ops accepts or rejects; null while PENDING |

**Composite index:** `(order_id, status, trigger_reason)` — used by the T-4 idempotency check.

**Status enum — `SuggestionStatus`**

| Value | Meaning |
|---|---|
| `PENDING` | Awaiting ops action in the dashboard |
| `ACCEPTED` | Ops approved — order moved to `recommendedAgent` |
| `REJECTED` | Ops rejected — order stays unchanged |

**Trigger enum — `TriggerReason`**

| Value | Meaning | UI Badge |
|---|---|---|
| `INITIAL` | Created at order creation or via manual API call | None |
| `AGENT_OFFLINE` | Auto-generated by T-4 loop when agent goes `OFFLINE` | `AGENTIC` |

**Domain invariant:** at most one `PENDING` + `AGENT_OFFLINE` suggestion may exist per order at a time (enforced in the T-4 service layer).

**Domain method — `resolve(SuggestionStatus)`**  
Always sets `status` and `resolvedAt` together so callers cannot forget the timestamp.

## Key Design Decisions

- **Lombok** (`@Getter`, `@Setter`, `@NoArgsConstructor`, `@ToString`) is used on all entities to eliminate boilerplate. The parameterised convenience constructors, `@PrePersist` hooks, and domain methods are written manually.
- **Lazy fetching** is used on all `@ManyToOne` and `@OneToMany` relations to avoid N+1 queries.
- **`@ToString(exclude = "orders")`** on `Agent` prevents triggering the lazy collection during logging.
- **Rich entity model** — `ReassignmentSuggestion.resolve()` enforces its own state-transition invariant rather than relying on the service layer.

## API Endpoints

| Method | Path | Purpose | Success |
|---|---|---|---|
| `POST` | `/orders` | Create an order pre-assigned to an agent (bumps `activeOrderCount`) | `201` + `Location` |
| `GET`  | `/orders?status=` | List orders; optional `OrderStatus` filter | `200` |
| `POST` | `/orders/{id}/suggest` | Run active routing strategy → persist a `ReassignmentSuggestion` (`INITIAL`); flips order to `REASSIGNMENT_PENDING` | `200` |
| `PATCH`| `/agents/{id}/status` | Update agent availability; publishes `AgentWentOfflineEvent` on transition → `OFFLINE` (fires T-4 loop) | `200` |
| `PATCH`| `/suggestions/{id}` | Resolve a `PENDING` suggestion (`ACCEPTED` / `REJECTED`); ACCEPT re-wires order & load counts | `200` |

**Errors** — `duplicate_order` 409 · `order_not_found` 404 · `agent_not_found` 404 · `illegal_agent_state` 409 · `suggestion_not_found` 404 · `illegal_suggestion_state` 409 · `no_available_agents` 409 · `unknown_routing_strategy` 500 · `validation_failed` 400 · `invalid_parameter` 400. Body: `{ error, message, timestamp, fields? }`.

## Routing Engine (T-2)

- **Contract**: `RoutingStrategy` takes a `RoutingContext(order, candidates, triggerReason)` → `List<Recommendation>`. Wrapping args in a context record means new inputs (sprint-2 zones) don't change the interface.
- **Runtime switchability**: `RoutingStrategyRegistry` holds `Map<String, RoutingStrategy>` auto-populated by Spring (bean name = `strategy.name()`). `active()` reads `routing.strategy` from `Environment` **on every call** — no cache, no restart. Startup validator fails fast if the configured name isn't registered.
- **Orchestrator**: `RoutingService.suggestFor(order, triggerReason)` — single method used by both `POST /orders/{id}/suggest` and the T-4 async listener. Loads `AVAILABLE` candidates, excludes the order's current assignee, calls the active strategy, persists the top rec, flips order to `REASSIGNMENT_PENDING`.
- **Config**: `routing.strategy=rule-based | ai` in `application.properties` (override with `ROUTING_STRATEGY` env var).

## AI Strategy (T-3)

- **Two distinct prompts** in `PromptBuilder` — INITIAL is a dispatch; REPLAN is a situation report (names the failed agent — inferred from `order.getAssignedAgent()` — declares the previous assignment void, frames as recovery).
- **Resilience layers** in `AiStrategy` — each caught, logged at WARN, falls back to `RuleBasedStrategy` with a `[fallback: <reason>]` prefix in the reasoning shown to ops:
  1. LLM transport / HTTP failure
  2. Response unparseable (empty / bad JSON / missing fields)
  3. Hallucinated `agentId` not in the candidate list
- **LLM config** (`application.properties`): `llm.provider` (gemini/groq/ollama), `llm.api-key` (from `LLM_API_KEY` env var), `llm.model`, `llm.base-url`.
- **Expected LLM output**: `{"agentId":"...","confidence":0.85,"reasoning":"..."}` — parser strips markdown fences and clamps confidence to `[0,1]`.

## Agentic Loop (T-4)

- **Trigger**: `AgentService.updateStatus` publishes `AgentWentOfflineEvent` only on transition to `OFFLINE` (same-status update is a no-op).
- **Consumer**: `AgentOfflineListener.onAgentWentOffline` with `@Async("replanExecutor") + @TransactionalEventListener(AFTER_COMMIT)` — fires only after publisher's transaction commits (no stale reads); runs on a bounded pool (PATCH endpoint returns immediately).
- **Affected orders**: assigned to that agent, status not in `{REASSIGNED, DELIVERED}`.
- **Idempotency**: per-order, skip if a `PENDING` + `AGENT_OFFLINE` suggestion already exists (uses `findByOrderIdAndStatusAndTriggerReason`). Same-agent double-flip won't dupe.
- **Failure isolation**: per-order try/catch; failures logged at WARN with counts (`replanned=x, skipped=y, failed=z`); AI-strategy fallback ensures a rule-based suggestion still lands if LLM is down.

## Behaviour Notes

- `OrderService.createOrder` — rejects OFFLINE assignee; increments agent's `activeOrderCount`.
- `AgentService.updateStatus` — idempotent on same status.
- `SuggestionService.resolve` — refuses non-`PENDING`; ACCEPT re-wires order + load counts; REJECT leaves order untouched (per product decision).
- DTOs always returned from controllers (entities never leak — avoids lazy-load surprises).
